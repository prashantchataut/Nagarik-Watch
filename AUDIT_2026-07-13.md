# Nagarik Watch — Critical Product, Newsroom and Engineering Audit

**Audit date:** 13 July 2026  
**Scope:** reader web app, newsroom/admin surfaces, content model, recommendation logic, deployment posture, design system, public trust and project-specific Skills.  
**Verdict:** **not launch-ready**, but now materially safer and more coherent after the first reconstruction pass.

## Executive verdict

Nagarik Watch did not primarily suffer from a lack of pages. It suffered from **false completeness**.

The repository contains 92 reader-facing page routes, 23 API routes and a large component surface, but route count was masking thin aliases, generic wrappers, empty content stores, simulated ranking signals and claims of functionality that were not supported by durable production data. The original interface compounded this by using a generic rounded-card/pill aesthetic, ad placements before the strongest journalism, an AI-generated-looking logo rationale, and repeated placeholder experiences.

The most serious issue was not visual. Three unused seed modules contained realistic-looking current-affairs reporting with invented bylines, direct quotes and unsupported details, while the actual local article store was empty. Those files could easily have been mistaken for publishable journalism. They have been removed.

The correct direction is not to imitate the visual noise of established portals. It is to combine their operational strengths—freshness, visible newsroom activity, strong section hierarchy, regional breadth and utilities—with a calmer reading experience, explicit provenance, honest algorithms and fewer fake surfaces.

## Severity assessment

### S0 — must block a public launch

1. **No verified production content pipeline is demonstrated end to end.** The local JSON store is empty. A live release must use Payload/Postgres with real editorial ownership, source records, verified publication metadata and durable media storage.
2. **Publisher identity is still placeholder-gated.** Legal entity, editor-in-chief, registration number, phone and registered address must be verified before `NEXT_PUBLIC_LAUNCH_STATUS=live`.
3. **A complete production build has not been reproduced in this execution environment.** The environment could not download `pnpm@10.17.1` from the npm registry. Static audits and syntax parsing passed, but dependency-aware typechecking, unit tests and Next builds must run in connected CI.
4. **Deployment logs supplied by the owner are still required.** Without the actual platform output, it would be dishonest to claim the reported deployment error is fixed.
5. **Audience ranking telemetry is not connected.** “Trending” and “Most Read” must not claim popularity ranking until event ingestion, anti-bot filtering, aggregation windows and observability are live.

### S1 — high priority before editorial beta

1. Consolidate the two admin concepts: Payload is the canonical CMS, while the web app also exposes operational `/admin` routes. Define ownership and remove duplicated editorial controls.
2. Replace remaining generic hub aliases with purpose-built behavior or deliberately remove them from navigation.
3. Add source, correction, update-history and verification fields to every real article workflow—not only the rendering layer.
4. Test Nepali typography, line breaks and input behavior on low-end Android devices and slow networks.
5. Add analytics contracts for impression, click, completion, bookmark, follow and hide events, with consent and retention rules.
6. Pin and reconcile framework versions. The monorepo currently resolves more than one Next.js version through different packages.
7. Add visual regression coverage for homepage, section, article, search, login, submission and admin-critical screens.

### S2 — progressive improvement

1. Expand province/local reporting templates only when a real editorial desk can maintain them.
2. Add election, disaster and result utilities behind verified official-source adapters and clear stale-data states.
3. Build membership only after the value proposition, entitlements, support and refund policy are real.
4. Add collaborative or embedding-based recommendations only after the simpler content/follow model has trustworthy data and measurable goals.

## Competitive benchmark

### What established Nepali portals do better

- **OnlineKhabar:** visibly fresh newsroom rhythm, dense entry points, strong latest/trending habits and useful service surfaces.
- **eKantipur:** stronger institutional hierarchy, section authority and a recognizable editorial masthead.
- **Ratopati:** broad category and provincial access, high update density, latest/popular pathways and many reader utilities.
- **Setopati:** clearer cover-story treatment, author presence, subscription prompts, multimedia and distinct editorial packages.
- **Techpana:** should remain a specialist benchmark for technology coverage, but its current page could not be reliably machine-inspected during this audit; no unsupported visual claims are made here.

### Where Nagarik Watch should be better

Nagarik Watch should not win by adding more boxes. It should win through:

1. **Calm density:** many useful entry points without turning every item into a rounded card.
2. **Visible trust:** author, source, verification, updates and corrections near the story—not buried in a policy page.
3. **Honest ranking:** no fabricated view counts, fake “live” states or unexplained personalization.
4. **Nepali-first typography:** Devanagari reading rhythm determines scale, line-height and measure; English is secondary.
5. **Public-service reliability:** official-source adapters, updated timestamps, stale/error states and source links.
6. **Editorial restraint:** ads and engagement modules never outrank the lead story or interrupt the opening paragraph.

## Critical findings and repairs

### 1. Brand and navigation

**Before:** generic eye/pen/sun mark, rounded container, pill-heavy navigation and a component-demo feeling.  
**Repair:** a flatter geometric “N/open record” mark, stronger Nepali wordmark, editorial rules, clearer active states and less decorative chrome.

### 2. Homepage hierarchy

**Before:** two ad surfaces could precede the lead story; the page lacked a convincing newsroom hierarchy.  
**Repair:** lead reporting now appears first, followed by secondary stories and a latest rail. Ads move below meaningful editorial content. Briefing, recommendations and section modules follow a clearer rhythm.

### 3. Article trust and reading flow

**Before:** billboard before headline, oversized headline, weak provenance and early interruption.  
**Repair:** headline scale is constrained, article metadata includes reading/update/trust cues, opening paragraphs remain uninterrupted and advertising moves into the body after the opening.

### 4. Generic hub pages

**Before:** generic wrappers reused synthetic ranking signals. “Trending” generated views and shares from array position.  
**Repair:** synthetic engagement was removed. Ranking pages now disclose that verified telemetry is not connected and use recency plus editorial priority as a temporary fallback. Hub pages use flatter editorial layouts and honest empty states.

### 5. Content integrity

**Before:** unused seed files contained fabricated current-affairs articles with invented quotes and bylines.  
**Repair:** those files were deleted. The remaining seed folder is documented as taxonomy/development fixtures only. A public **Source Desk** exposes RSS headline, timestamp and original-publisher link without copying article bodies or presenting external reporting as Nagarik Watch work.

### 6. Recommendation engine

**Before:** author follows created terms that story vectors never contained; the dominant strategy ignored some declared strategies; future and sponsored items could remain eligible; fatigue logic was wrong; diversity was weak; roadmap comments overstated implementation.  
**Repair:** `nw-hybrid-v2` now includes author terms, explicit follow matching, future/invalid-date filtering, sponsored exclusion by default, corrected fatigue handling, category/author/source caps and transparent version logging. Collaborative and embedding ranking remain explicitly unimplemented.

### 7. Workflow and publishing state

**Before:** shared types exposed five workflow stages while Payload exposed fourteen; public queries could expose retracted items or omit updated items depending on store.  
**Repair:** workflow types were unified. Public visibility is restricted to `published` and `updated`; retracted and intermediate states are excluded.

### 8. Admin honesty

**Before:** dashboard wording represented scheduled public stories as drafts, and algorithm pages implied capabilities beyond the implementation.  
**Repair:** labels now match the data source, canonical-CMS limitations are stated, and the algorithms page shows version, guardrails and actual boundaries.

### 9. CI and deployment posture

**Before:** a stronger `ci.yml` existed at the repository root where GitHub would not run it, while `.github/workflows/ci.yml` ran a reduced check set.  
**Repair:** the real GitHub workflow now runs formatting, linting, typechecking, tests, static audits, web build and DB tests with Node 22 and pnpm 10.17.1. The misleading root duplicate was removed.

## Verification performed

Passed in the available environment:

- public-surface audit
- ad-placement audit
- architecture audit
- repository recovery verification
- project-specific newsroom audit: 0 failures, 6 warnings
- syntax parsing of every modified TS/TSX file with TypeScript 5.8.3
- skill validation

Not completed in this environment:

- `pnpm install --frozen-lockfile`
- dependency-aware `pnpm typecheck`
- unit/integration/e2e tests
- Next.js production builds for web and admin

Reason: Corepack could not fetch the pinned pnpm binary from the npm registry. This is an execution-environment network/tooling limitation, not proof that the application build is healthy.

## Release contract

Do not mark the portal live until all of the following are true:

1. Connected CI completes the complete workflow with a frozen lockfile.
2. The owner’s real deployment logs are reproduced and resolved.
3. `NEXT_PUBLIC_LAUNCH_STATUS=live pnpm launch:gate` passes with verified identity, secrets, Payload, Postgres and durable media storage.
4. At least one real article completes draft → fact check → edit → publish → update → correction/retraction testing.
5. Public pages contain no fabricated stories, fake metrics, fake live states or placeholder organization details.
6. Accessibility and mobile visual regression checks pass on representative devices.
7. Recommendation telemetry has explicit event definitions, bot filtering, retention and monitoring before popularity labels are enabled.

## Final product position

The strongest version of Nagarik Watch is not “another Nepali portal with more modules.” It is a **trust-first, Devanagari-first public-interest newsroom product**: fast enough for breaking news, calm enough for serious reading, explicit about sources and corrections, and honest about what its algorithms know.
