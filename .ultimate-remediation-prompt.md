## WHAT THIS PROJECT IS

**Name:** Nagarik Watch (नागरिक वाच)
**What:** Devanagari-first digital news portal for Nepali readers, run as civic-minded watchdog journalism
**Stack:** pnpm monorepo + Turborepo, Next.js 15 App Router (apps/web), Payload CMS 3 (apps/admin), Postgres + Better Auth, shared packages (db/infra/ingest/ui/tsconfig), Playwright e2e, Vitest

- Mobile that does NOT shrink desktop — different layout entirely on phones
- A masthead with the brand mark and date, not three lines of marketing copy under the logo
- A footer with REAL navigation: about, ethics, corrections, contact, privacy, terms, advertise
- Trust signals visible on every article: byline, date, author page, source attribution
- Corrections shown as part of the article, not hidden

## THE CURRENT BROKEN STATE — WHAT I ALREADY KNOW

I verified these issues exist. Some I'm certain about, some I'm not. Verify each one yourself before fixing — there may be nuance I missed.

### A. Admin login — BROKEN, shows Nepali "email or password didn't match"
Test credentials exist in `.env`: `superadmin@nagarikwatch.com` / `nagarikwatch@superadmin_`.
The login form posts to Better Auth's `/api/auth/sign-in/email`. Better Auth uses Postgres when `DATABASE_URL` is set, else falls back to in-memory PGlite. Postgres is not currently running. Seed boot accounts (`seedBootAccounts`) silently fail with `.catch(() => {})`. So when Postgres is down, no accounts exist, login returns generic error, and the developer (me) is staring at the screen wondering why the password "doesn't match" when it's correct.

Investigate: Is the DB connection stable? Is PGlite actually usable in dev? Should we switch to PGlite by removing `DATABASE_URL` from `.env` for local dev, or set up Postgres properly? The fix should be one where login ACTUALLY works end-to-end, including boot-seed creation, session persistence, and redirect to `/admin/dashboard`.

### B. UI/UX is "terrifying" — looks like AI-slop, broken on multiple surfaces
I'm not going to tell you exactly what's wrong with the UI — that's your job to find and fix. But here are hints:
- The current `<Logo>` component renders three lines of text under the logo mark. The third line "PUBLIC INTEREST NEWS" reads like a generic tagline / watermark. It needs to go or be replaced with something cleaner. The user perception of "Ello, a Nepali news portal" tagline is specifically this third line.
- Run the "category-reflex test" from `design-anti-slop`: if a stranger could guess the aesthetic from "Nepali news portal" alone, you've failed. The Civic Crimson palette was chosen specifically to avoid tabloid-red, navy-SaaS, or generic-editorial. Use it.
- Walk every page and ask: "Is this template-y?" If yes, fix it.
- Run `impeccable critique` on the homepage, article page, category page, admin panel, login pages, and footer. Apply the critique.
- The article reading experience should feel like a real newspaper website, not a SaaS blog. Check line length, line height, font hierarchy, byline placement, image treatment, pull quotes, corrections, related stories.
- Mobile is not "shrunken desktop". Inspect the masthead, nav, article body, and admin panel on mobile widths. Fix anything that looks like a responsive afterthought.
- WCAG 2.1 AA. Run an accessibility audit. Fix focus rings, contrast, keyboard nav, semantic HTML, ARIA where needed, alt text on every image.

### C. Theme toggle / locale toggle interaction
I observed that toggling language sometimes feels like it also toggles theme. I could not find direct code coupling — `swapLocale` in `apps/web/lib/i18n/locales.ts` is a pure URL string function, and `ThemeToggle` only uses `locale` for label translation. The issue might be:
- A first-paint flash on navigation (the inline theme script in `apps/web/app/[locale]/layout.tsx` might run after navigation, not just on first load)
- A `matchMedia` listener missing for system-preference changes
- A localStorage race condition
- A re-render causing the toggle button state to flicker

Investigate, reproduce, and fix the actual cause — don't just patch the symptom.

### D. Admin panel — most pages non-functional
The `/admin/*` routes surface ~23 pages. I believe only 5 are functional. The others have disabled buttons ("needs Payload config"), empty tables, or "Persistence not wired" messages. Investigate EVERY admin page yourself; don't trust my list.

Architecture context (verify this yourself):
- `apps/admin` (port 3001) is Payload CMS — fully featured, Postgres-backed, with collections for Articles, Users, Categories, Tags, Authors, Media. Access control via `apps/admin/src/access/rbac.ts` with 19 newsroom roles.
- `apps/web/app/admin` is the custom newsroom UI on the reader site. Uses Better Auth for sessions. Uses the JSON store OR Payload as content source (`PAYLOAD_CONTENT_SOURCE` env var).
- The two systems are supposed to coexist — Payload is the source of truth for content; the web admin is the editor's day-to-day surface.

Decide: should the web admin pages talk directly to the JSON store / Payload, or should they be hidden in favor of Payload? Either path is valid, but PICK ONE and make it consistent.

### E. Journalist login — DOES NOT EXIST
The user wants a SEPARATE journalist login. NOT in `/admin`. Journalists should not see the full admin panel — they should see a simplified interface for their own articles.
- Currently, journalists log into `/admin/*` with the `journalist` role and see everything (or get 404s because their role can't access most pages).
- The user wants a dedicated `/journalist/login` + `/journalist/dashboard` flow.
- Journalist dashboard should show: their assigned articles, "create new" button, draft/submit workflow, profile. NO admin controls.
- Server-side gated to `journalist` role and above — admins can access journalist pages but journalists can't access admin pages.

### F. User login — DOES NOT EXIST
Better Auth supports reader accounts (with `reader` role) but there is no `/login`, `/register`, `/profile`, or `/saved` page on the public site. The site mentions "Saved" in the masthead but the link leads nowhere useful.
- Build a reader login + registration flow
- Build a reader profile page (reading history, bookmarks, preferences)
- Wire the bookmark button on article cards to actually save
- Build a `/saved` page that shows bookmarked articles

### G. Admin role hierarchy
19 roles are defined in `apps/admin/src/access/rbac.ts` and `apps/web/lib/admin-roles.ts`. But the admin panel doesn't surface this hierarchy clearly. The `/admin/roles` page is read-only. The `/admin/users` page only shows the current user.
- Make role management visible and editable (for super_admin)
- Make user management actually list users and allow role assignment
- Make the permission boundary between roles visible in the UI

### H. Live data — almost all mocked
The site has 13+ live data providers (weather, AQI, NEPSE, gold/silver, forex, sports, football, cricket, election, exam, disaster, parliament, YouTube). Currently:
- Weather (Open-Meteo) and AQI (Open-Meteo) work with no API key — but the health check incorrectly marks them unhealthy because it expects `WEATHER_API_KEY`. The user shouldn't need an API key for Open-Meteo.
- Forex (NRB daily feed) works with no API key but needs the NRB feed to be properly parsed.
- NEPSE scrapes nepalstock.com via regex — fragile, breaks on layout changes.
- Everything else returns mock data.
- There are TWO live data systems: `apps/web/lib/live-data.ts` (old, all-mock) and `apps/web/lib/live/` (new, partial real). The old one should probably be deleted and all widgets unified on the new one.

Investigate:
- Which providers can be made real without API keys?
- Which need API keys (and which keys are free to obtain)?
- For the rest, build an admin panel where editors can MANUALLY update the data (don't hardcode mock values in source code — make them editable in the CMS)

The-widget-integration skill is mandatory here. Every widget must show source, timestamp, loading state, error state, and mock status. A failed provider must NOT break the homepage.

### I. Paywall — type system only, no enforcement

### J. Reader submissions — no form, just a workflow diagram

The user specifically wants **literature (साहित्य)** added — and more diverse categories like technology, health, education, interview, photo-story, video.

### M. Production data persistence — broken on Vercel
The JSON article store writes to `process.cwd() + '/data/articles.json'`. On Vercel, the filesystem is read-only at runtime. Writes silently fail with `console.error('[json-store] write error:', err)` and the article is lost.
- Fix the silent failure — surface the error to the user
- Add `ARTICLES_STORE_URL` env var for blob storage, OR migrate everything to Payload
- Document this in `.env.example` (currently undocumented)
