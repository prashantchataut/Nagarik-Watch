# Nagarik Watch notification system

The notification product has two separate delivery surfaces. Do not describe them as one feature.

## 1. In-app alert desk

This works whenever the reader can reach the web application and the operational PostgreSQL database is configured.

- Readers follow desks, topics and journalists from **My news desk**.
- The site creates notification events only from canonical published Payload stories.
- Events are eligible for breaking, followed-topic, followed-author or daily-digest treatment.
- Receipts keep three meanings separate: `seen` means surfaced, `read` means deliberately opened, and `delivered` exists only in the push-delivery log.
- Opening the inbox never consumes interruptive Web Push quota.
- A foreground browser alert is shown at most once per event while the inbox can remain unread.
- Quiet hours do not hide the in-app inbox; they govern interruptive delivery only.
- Marketing alerts remain disabled.

## 2. Background browser push

Background push requires all of the following:

```text
NEXT_PUBLIC_WEB_PUSH_VAPID_KEY=<public VAPID key>
WEB_PUSH_PROVIDER_URL=https://<push-provider>/deliver
WEB_PUSH_PROVIDER_API_KEY=<provider bearer token>
CRON_SECRET=<32+ random characters>
```

The reader app stores browser subscriptions in `nw_push_subscriptions`. Vercel calls `/api/notifications/deliver` hourly. The endpoint accepts only:

```text
Authorization: Bearer <CRON_SECRET>
```

The reader app then sends the provider this HTTPS request:

```json
{
  "subscription": {
    "endpoint": "https://push-service.example/...",
    "expirationTime": null,
    "keys": {
      "p256dh": "...",
      "auth": "..."
    }
  },
  "notification": {
    "title": "Nagarik Watch",
    "body": "...",
    "url": "/news/story-slug",
    "tag": "notification-event-id"
  },
  "metadata": {
    "eventId": "...",
    "subscriptionId": "...",
    "readerLocale": "ne"
  }
}
```

The provider must return a 2xx response only after the Web Push request is accepted. A `404` or `410` from the browser push service should be returned to Nagarik Watch so the subscription can be disabled.

## Editorial contract

A reporter may recommend an alert, but cannot directly send one.

1. Reporter selects story tags.
2. Reporter selects `none`, `followers`, or `breaking` as a recommendation.
3. Alert audience tags must be a subset of story tags.
4. An editor reviews the story, evidence, classification and alert recommendation.
5. Only a published or updated canonical Payload story creates a reader event. Author and tag relationship IDs are resolved to canonical slugs before audience matching.
6. The delivery planner applies reader preferences, freshness, daily quota, cooldown, retry cap and timezone-aware quiet hours.

## Current policy

- daily interruptive ceiling: 8 alerts per reader
- breaking cooldown: 15 minutes
- followed-topic/author cooldown: 45 minutes
- delivery retry cap: 5 attempts
- quiet hours: reader-controlled, interpreted in the reader's stored IANA timezone
- non-urgent alerts wait during quiet hours
- breaking alerts may bypass quiet hours
- sponsored, retracted, future-dated and do-not-recommend stories are ineligible

## Service worker behavior

`/sw.js` is generated by a Next route.

- It does not cache API, account, saved, reader-desk, journalist or admin routes.
- It accepts only same-origin public notification destinations.
- Invalid or non-JSON push payloads fail safely.
- Notification clicks focus an existing Nagarik Watch tab or open a same-origin route.
- Public navigations remain network-first; personalized pages are never stored in the service-worker cache.

## Release test

1. Subscribe in a clean browser profile.
2. Confirm the row exists in `nw_push_subscriptions`.
3. Publish a test story with a matching followed topic.
4. Confirm an event exists and appears in the in-app alert desk.
5. Invoke `/api/notifications/deliver` with the cron bearer token.
6. Confirm one provider request and one delivery row.
7. Repeat immediately and confirm cooldown suppression.
8. Test a non-breaking event during the reader's quiet hours.
9. Test a provider failure and confirm retry count increments without exceeding five.
10. Unsubscribe and confirm the subscription becomes inactive.

Do not call background push production-ready until this test passes in both preview and production.
